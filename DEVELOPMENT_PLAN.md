# План развития ASP Classic Language Support

Документ фиксирует текущее состояние проекта и порядок реализации функциональности. Его цель — служить рабочим ориентиром при развитии плагина.

## Текущее состояние

Проект находится в рабочем MVP-состоянии и уже пригоден для повседневной
навигации по реальному ASP Classic-проекту:

- распознаются `.asp`, `.inc` и `.vbs` файлы;
- ASP-файлы разбиваются на HTML-части и VBScript-блоки `<% ... %>` / `<%= ... %>`;
- работает базовая подсветка синтаксиса ASP/VBScript;
- несколько scriptlet-блоков одного ASP-файла объединяются в единый VBScript-контекст;
- есть парсер VBScript и набор PSI-элементов;
- работает scope-aware `Go To Definition` внутри файла и по цепочкам include;
- работает `Find Usages` для локальных и подключаемых символов;
- include-директивы индексируются, поддерживают навигацию и обратный поиск;
- работает базовый completion для VBScript/ASP built-ins, текущего scope и
  транзитивно подключённых include-файлов;
- resolve и Find Usages используют кэшируемые таблицы символов и быстрый
  предварительный поиск кандидатов;
- полный аудит TTS обрабатывает 2477 файлов без зависаний; 2425 файлов
  разбираются без диагностик;
- есть smoke/regression/integration-тесты для lexer, parser, injection,
  resolve, include и Find Usages;
- собрана пригодная для ежедневной установки версия `0.0.2`.

## Главные проблемы

1. Базовый completion реализован, но пока нет типизированных подсказок членов
   пользовательских классов/объектов и контекстного ранжирования.
2. Нет форматтера для VBScript и ASP scriptlet-блоков.
3. Нет стандартных IDE-функций: brace matcher, commenter, folding и
   structure view.
4. Resolve ещё не использует stub index для произвольных проектных символов и
   требует дальнейших тестов сложного shadowing/class-member поведения.
5. Не реализованы inspections для unresolved identifier, отсутствующих include
   и неиспользуемых объявлений.
6. В проекте есть отладочные/шаблонные элементы, которые нужно убрать или
   спрятать перед публикацией.
7. Остались 52 неоднозначных файла TTS для отложенной ручной классификации.

## Что не делаем

- Дебаггер VBScript/ASP Classic не входит в актуальный план работ.
- Интеграция с Windows Script Debugger / PDM не является блокером для развития плагина.
- Упоминание дебаггера нужно убрать из пользовательского roadmap перед публикацией.

## Приоритеты реализации

### 1. Производительность на больших файлах — базовый этап выполнен

Это самый важный технический риск: плагин должен оставаться отзывчивым на реальных legacy-проектах с большими `.asp` и `.inc` файлами.

Выполнен полный parser-аудит TTS: 2477 файлов обрабатываются без зависаний,
а прежние 24 патологически медленных файла разбираются за десятки миллисекунд.
Resolve и Find Usages больше не выполняют безусловный полный поиск по проекту.

Дальнейший план:

- Замерить проблемные сценарии:
  - открытие большого ASP-файла;
  - первичная lexing/parsing/injection обработка;
  - редактирование внутри VBScript-блока;
  - подсветка и annotator pass;
  - resolve/navigation на большом файле.
- Добавить или расширить performance/smoke-тесты на больших файлах:
  - использовать реальные данные из `src/test/testData/asp/real-world` и `external-project`;
  - зафиксировать допустимые лимиты времени для базовых операций;
  - отдельно проверять файлы с большим количеством `<% ... %>` блоков.
- Проверить `AspLexer`:
  - минимизировать лишние аллокации строк и диапазонов;
  - убедиться, что переходы между HTML и VBScript-блоками линейные;
  - проверить поведение на незакрытых scriptlet-блоках.
- Проверить multi-host injection:
  - не склеивать и не пересчитывать весь файл без необходимости;
  - избегать тяжёлого обхода PSI при каждом вызове injector;
  - кэшировать вычисления только через безопасные IntelliJ-механизмы (`CachedValuesManager`, `PsiModificationTracker`), если это действительно нужно.
- Проверить подсветку и debug-компоненты:
  - отключить или удалить debug annotator для обычного режима;
  - убедиться, что annotator не обходит весь файл на каждый pass;
  - оставить диагностические инструменты только за internal-флагом или test-only использованием.
- Контролировать производительность resolve/completion:
  - не выполнять проектный поиск при каждом вызове completion;
  - повторно использовать кэшируемую таблицу символов и include-граф;
  - не запускать дорогой resolve из подсветки/аннотаций без необходимости.

Критерий готовности:

- большие ASP/INC-файлы открываются и редактируются без заметных зависаний IDE;
- performance-тесты фиксируют регрессии;
- debug-компоненты не влияют на обычную работу пользователя.

### 2. Форматирование VBScript и ASP scriptlet-блоков

Форматирование остаётся важной ежедневной функцией при сопровождении
legacy-кода, но требует отдельной осторожной работы с HTML и scriptlet-границами.

План работ:

- Зарегистрировать formatter для `VbScriptLanguage`:
  - реализовать `FormattingModelBuilder`;
  - построить дерево `Block` для основных PSI-узлов;
  - подключить spacing/indent rules;
  - добавить минимальные code style settings, если дефолтов недостаточно.
- Реализовать базовые отступы:
  - `If ... Then` / `ElseIf` / `Else` / `End If`;
  - `Select Case` / `Case` / `End Select`;
  - `For` / `Next`;
  - `For Each` / `Next`;
  - `Do` / `Loop`;
  - `While` / `Wend`;
  - `Sub` / `End Sub`;
  - `Function` / `End Function`;
  - `Class` / `End Class`;
  - `With` / `End With`.
- Реализовать spacing rules:
  - пробелы вокруг бинарных операторов;
  - пробел после запятой в аргументах;
  - отсутствие лишних пробелов перед `)` и после `(`;
  - аккуратное форматирование присваиваний `=`;
  - сохранение строковых литералов и комментариев без повреждений.
- Поддержать ASP scriptlet-контекст:
  - форматировать VBScript внутри `<% ... %>`;
  - не ломать HTML-части файла;
  - корректно обрабатывать `<%= expression %>` как expression-блок;
  - сохранить границы scriptlet-блоков и не переносить код между HTML и ASP без явной необходимости.
- Восстановить и проверить HTML-форматирование внутри `.asp` / `.inc`:
  - HTML formatter должен работать для ASP-файлов так же предсказуемо, как для обычного HTML;
  - хаотично расставленные HTML-теги из WYSIWYG-редакторов должны приводиться к нормальной вложенной «лесенке»;
  - ASP scriptlet-блоки должны участвовать в HTML-дереве как специальные узлы, но не отключать стандартные правила HTML-отступов;
  - отдельно проверить, не мешают ли `AspFileViewProvider`, template-data элементы, outer elements или lexer-разбиение запуску стандартного HTML formatter.
- Реализовать уточнённый стиль `control-flow scriptlets around HTML`:
  - управляющая VBScript-конструкция может открывать HTML-фрагмент через отдельный `%>` на уровне вложенности VBScript-блока;
  - HTML внутри ветки форматируется обычным HTML formatter и получает свой HTML-indent;
  - продолжение VBScript (`Else`, `Next`, `End If`, `Loop` и т.п.) возвращается в отдельный `<% ... %>` блок;
  - VBScript-код внутри каждого multiline scriptlet-а начинается на том же уровне отступа, что и открывающий `<%`, а вложенность создаётся только VBScript-конструкциями;
  - formatter не должен превращать такой стиль обратно в компактные inline-control scriptlets вроде `<% If condition Then %>` без явной настройки.

Пример целевого форматирования `control-flow scriptlets around HTML`:

```asp
<%
If items.Count > 0 Then
    %>
    <ul>
        <%
        For Each item In items
            %>
            <li><%= item.Name %></li>
            <%
        Next
        %>
    </ul>
    <%
Else
    %>
    <p>No items</p>
    <%
End If
%>
```
- Добавить тесты форматтера:
  - отдельные `.vbs` тесты;
  - `.asp` тесты с HTML + несколькими scriptlet-блоками;
  - тесты на комментарии `'`;
  - тесты на вложенные конструкции;
  - тесты на HTML из WYSIWYG-редакторов с хаотичными отступами;
  - тесты на развёрнутые `control-flow scriptlets around HTML`, где `%>` / `<%` стоят отдельными строками;
  - тесты на неполные/ошибочные конструкции, чтобы formatter не падал.

Критерий готовности:

- `Reformat Code` работает для `.vbs`, `.asp`, `.inc`;
- форматтер не портит HTML и scriptlet delimiters;
- HTML внутри `.asp` / `.inc` форматируется вложенной лесенкой;
- покрыты основные управляющие конструкции VBScript;
- форматтер устойчив к частично некорректному legacy-коду.

### 3. Include support — MVP выполнен

Поддержка include важна для реальных ASP-проектов, потому что большая часть общей логики находится в `.inc` файлах.

Реализовано:

- распознавание include-директив:
  - `<!-- #include file="relative/path.inc" -->`;
  - `<!-- #include virtual="/absolute/from/site/root.inc" -->`.
- reference/navigation на путь include;
- resolve относительно текущего файла и корня проекта;
- индекс обратных зависимостей и транзитивный include-граф;
- cross-file `Go To Definition`, `Find Usages` и completion;
- integration-тесты относительных, virtual, вложенных и циклических include.

Осталось:

- inspection для отсутствующих include-файлов;
- дополнительные тесты нестандартных web-root/content-root конфигураций.

Критерий готовности:

- IDE понимает пути в include-директивах;
- работает переход к подключаемому файлу;
- отсутствующие include можно диагностировать отдельной inspection в будущем.

### 4. Базовые IDE-функции для удобства редактирования

План работ:

- Добавить commenter:
  - VBScript line comment через `'`;
  - учитывать, что ASP Classic не использует `<%-- --%>`.
- Добавить brace/keyword matcher:
  - `If` ↔ `End If`;
  - `Sub` ↔ `End Sub`;
  - `Function` ↔ `End Function`;
  - `Class` ↔ `End Class`;
  - `Select` ↔ `End Select`;
  - `With` ↔ `End With`.
- Добавить folding:
  - блоки `Sub`, `Function`, `Class`;
  - крупные `If`, `Select`, циклы;
  - ASP scriptlet-блоки при необходимости.
- Добавить structure view:
  - top-level `Sub`;
  - top-level `Function`;
  - `Class`;
  - `Property`.

Критерий готовности:

- редактирование `.asp`, `.inc`, `.vbs` становится удобнее даже без сложного resolve;
- функции не создают заметной нагрузки на больших файлах.

### 5. Completion — базовый этап реализован

Реализовано:

- keyword completion для VBScript;
- completion для встроенных ASP-объектов:
  - `Request`;
  - `Response`;
  - `Session`;
  - `Application`;
  - `Server`.
- базовые члены встроенных объектов:
  - `Response.Write`;
  - `Request.QueryString`;
  - `Request.Form`;
  - `Server.CreateObject`;
  - `Server.MapPath`.
- видимые параметры, переменные, константы, процедуры, функции, свойства и
  классы текущего scope;
- top-level символы из транзитивного include-графа;
- фильтрация невидимых локальных и ещё не объявленных implicit-переменных;
- подавление подсказок внутри строк/комментариев и после точки неизвестного
  объекта;
- case-insensitive lookup и integration-тесты для `.vbs` и injected ASP.

Осталось:

- типизированный member completion для пользовательских классов и объектов;
- контекстное ранжирование и insert handlers для конструкций с параметрами;
- при появлении stub index — completion проектных символов вне include-графа.

Критерий готовности:

- completion помогает писать типовой ASP/VBScript-код;
- список подсказок не требует полного resolve всего проекта на каждый вызов.

### 6. Go To Definition, Find Usages и symbol resolve — MVP выполнен

Однофайловая и include-навигация уже работает, как и обратный поиск
использований. Дальнейшая работа относится к расширению модели символов и
масштабированию, а не к созданию механизма с нуля.

Реализовано:

- resolve с учётом scope:
  - локальные переменные внутри `Sub` / `Function`;
  - параметры;
  - top-level declarations;
  - implicit assignment declarations;
- кэшируемая таблица символов файла;
- include-граф для cross-file navigation и usages;
- быстрый предварительный поиск кандидатов для глобального Find Usages;
- тесты shadowing, локальных символов, include-цепочек и циклов.

Осталось:

- полноценная модель class members и `With` blocks;
- уточнение поведения `Option Explicit`;
- stub/index для top-level символов вне include-графа:
  - `Sub`;
  - `Function`;
  - `Const`;
  - `Class`;
  - `Property`.

Критерий готовности:

- local resolve корректен внутри одного файла;
- cross-file resolve работает для include-сценариев;
- resolve не ухудшает производительность больших файлов.

### 7. Inspections

План работ:

- Добавить inspection для unresolved identifier после стабилизации resolve.
- Добавить inspection для отсутствующего include-файла.
- Позже добавить inspection для unused `Dim` / `Const`.
- Не включать тяжёлые inspections до завершения оптимизаций производительности.

Критерий готовности:

- inspections помогают находить реальные ошибки;
- inspections не создают лагов при редактировании больших файлов.

### 8. Санитарная очистка перед публикацией

План работ:

- Удалить шаблонные элементы, не относящиеся к плагину.
- Проверить `plugin.xml`:
  - убрать template/toolWindow-мусор;
  - убрать неактуальный resource bundle, если он не используется;
  - добавить корректные marketplace metadata;
  - добавить `change-notes`;
  - проверить `since-build` / `until-build`.
- Удалить резервные и временные файлы вроде `*.java~`.
- Debug actions/annotators/activity оставить только если они нужны и спрятаны от обычного пользователя.
- Обновить `README.md`:
  - убрать Debugger из roadmap;
  - явно указать приоритеты: performance, formatter, include, completion;
  - описать фактические возможности navigation, Find Usages и completion.

Критерий готовности:

- проект не содержит template-мусора;
- README и plugin metadata соответствуют фактическому состоянию;
- плагин готов к дальнейшей подготовке к публикации.

   набор встроенных функций и членов объектов по результатам использования.
2. Добавить commenter, folding, structure view и matcher.
3. Реализовать минимальный formatter для `.vbs`.
4. Расширить formatter на VBScript-блоки внутри `.asp` / `.inc` и добавить
   formatting/performance regression-тесты.
5. Расширить модель scope/class members и при необходимости добавить stub index
   для проектных символов вне include-графа.
6. Добавить безопасные inspections.
7. Выполнить санитарную очистку и актуализировать metadata перед публикацией.
8. Вернуться к ручной классификации оставшихся 52 файлов TTS из
    [`docs/TTS_PARSER_REVIEW_BACKLOG.md`](docs/TTS_PARSER_REVIEW_BACKLOG.md):
    отделить реальные ошибки исходников от валидных, но пока не поддержанных
    конструкций VBScript и служебных файлов.
